# ADR-0020: Operations security and backups (M14b)

- **Status:** Accepted
- **Date:** 2026-10-11
- **Milestone:** M14 (the operations half, "M14b"; CSP, WebAuthn, step-up and the supply-chain checks are the other half)

## Context
SPEC §11 and §17 ask for:
- encrypted backups with a restore drill, `make backup` and `make restore-test`;
- CrowdSec;
- key rotation;
- retention jobs for personal data;
- runbooks for rollback, key rotation, a database restore, rebuilding the search index, a leaked credential and incident response;
- an SSL Labs A+.

The threat model adds G-35 to G-39 and G-41 to G-43:
- Traefik held the Docker socket;
- one database role owned everything;
- Valkey had one password for all clients;
- containers kept their default capabilities;
- redis-state had no `maxmemory`;
- nothing on the server was backed up.

The constraints:
- **One host:** production is one 16-core, 15 GB host without a GPU that runs everything, and it is already live with data (M12 and M13 tables). It is updated with `install.sh --update`, so every change has to arrive safely through that path.
- **Configuration in the admin:** every operator setting is editable in the admin (ADR-0019); `.env` is for bootstrap only.
- **Licences:** dependencies must be permissive; GPL/AGPL tools only as separate processes.
- **Development:** the dev stack is shared by several builders and test lanes, and must keep working.

## Decision

### 1. Backups: pgBackRest for the database, restic for files and offsite
- **Database:**
  - pgBackRest 2.59 takes a full backup weekly (`backups.full_weekday`) and a differential on the other nights (`backups.schedule_time`, `backups.schedule_timezone`), and keeps `backups.db_full_retention` fulls (2).
  - PostgreSQL archives WAL continuously (`archive_command`, `archive_timeout` 300 s), so a restore can reach any moment in between: at most 5 minutes of data at risk.
  - The repository is encrypted (AES-256-CBC) and compressed (zstd).
- **Files:** restic 0.19 snapshots `.env`, `secrets/`, the artwork, a logical `pg_dump -Fc` (a second, tool-independent copy) and, when `backups.media_enabled`, the media libraries. Retention is `backups.files_keep_daily/weekly/monthly`.
- **Offsite (optional):** an S3-compatible bucket set in **Settings → Backups**, with the keys as encrypted settings. It gets a restic snapshot of the pgBackRest repository every `backups.offsite_interval_minutes`, plus `restic copy` of the night's local snapshots. One tool talks to S3: no pgBackRest S3 repository, no second set of S3 code paths.
- **Encryption:** one passphrase, `secrets/backup_passphrase`, generated by `scripts/secrets.sh` and shown once by the installer, is both pgBackRest's cipher pass and restic's password. It never reaches Django, a command line or a log.
- **Storage:** the backups live in `BACKUP_DIR` (default `/var/backups/smart-iptv`; the installer recommends another disk), mounted into PostgreSQL (for `archive_command`) and the backup service.

### 2. A thin agent, with the decisions in Django
- **The `backup` service** runs the `backup` target of `docker/postgres.Dockerfile`: the same PostgreSQL binaries as the database, plus pgBackRest, restic and python3. It runs `apps/ops/agent.py`, stdlib only and no Django, like `apps.live.relay`.
- **Polling:** every 30 s it posts its status to `web:8000/internal/backups/agent/poll` with a bearer token (`BACKUP_AGENT_TOKEN`, internal network only). It gets back its configuration and at most one job, runs it, and posts the result to `/jobs/<id>`.
- **Django** (`apps/ops/backups.py`, beat every minute) owns:
  - the schedule;
  - `BackupRun` rows (queued, running, succeeded, failed; claimed with `skip_locked`);
  - lost-run expiry;
  - the drill verdict;
  - alerts and metrics.
  
  Everything the operator sees is in the database and the admin.
- **WAL archiving** switches on only when the agent has created the stanza: it writes `/backup-config/archive.enabled`, which `pgbackrest-iptv-archive` checks. Without that flag, WAL is released, so a server with backups off, or before the first run, never fills its disk with WAL. Turning backups off removes the flag.
- **The admin's Backups page** (permissions `backups.view` and `backups.run`) shows:
  - the last runs, the last drill (restore time, checks and row counts), the next runs, free space and the agent's health;
  - **Back up now**, **Run the restore drill** and **Test the destinations** (each audited).

### 3. The restore drill
It runs weekly (`backups.drill_weekday`, `backups.drill_time`), after the first backup on a new server, and on demand (`make restore-test` in development, and in `make ci`).
1. `pgbackrest restore` of the latest backup into the `backup-drill` volume with every archived WAL file.
2. A throwaway PostgreSQL starts with no TCP listener, a private socket and archiving off.
3. The agent reads its migrations and row counts and runs `pgbackrest verify`.
4. Django judges the result. It fails on missing migrations, missing tables, an empty table that isn't empty live, data more than 26 hours old (WAL archiving stopped) or verify errors.

The restore time is recorded as the measured recovery time objective.

### 4. Alerts through the M13 path
- **The six alerts:** BackupFailed, RestoreDrillFailed, BackupStale (26 h), RestoreDrillStale (8 days), BackupAgentDown (10 minutes silent) and WalArchiveFailing (`pg_stat_archiver`).
- **Who delivers them:** with the monitoring overlay, they are Prometheus rules on `iptv_backup_*` metrics; without it, Django delivers them itself through `apps.notifications.alerts.deliver()`, with firing and resolved state in redis-state. So a server without monitoring still hears about failed backups.
- **New servers:** a 6-hour grace keeps a new installation quiet until its first backup.

### 5. Restores
- **In place, to a moment** (`latest`, a time, or `name:<restore point>`): the `restore` service (profile `restore`, no network) runs `agent.py restore-db --target … --yes` with PostgreSQL stopped. PostgreSQL then replays WAL to the target and promotes.
- **Restore points:** `install.sh --update` creates `pre-update-<UTC time>` before pulling, so an update's migrations can be undone.
- **Single files:** with restic.
- **Disaster recovery onto a new server:** from `BACKUP_DIR` or the bucket.
- **Tested** on a throwaway compose project: a point-in-time restore of a 17 MB database took 27 s and came back on timeline 2, and later backups and drills worked. [docs/runbooks/backups.md](../runbooks/backups.md) and [rollback.md](../runbooks/rollback.md) have the steps.

### 6. Personal-data retention
A daily job (`ops-apply-retention`, 04:20) applies the `privacy.*` settings in batches and audits the counts as `privacy.retention`:
- the IP address and user agent of ended playback sessions blanked after 30 days, and the sessions deleted after 365 (minimum 90, for the dashboard);
- watch history after 365 days, and resume points after 730;
- the audit log after 730 days (minimum 365), and billing entries after 2190 (minimum 1826);
- the notification log and failed admin sign-ins after 90 days;
- payment webhooks' raw payloads emptied after 365 days;
- expired sessions at once.

The audit log stays append-only: a `SECURITY DEFINER` function, `audit_purge(days, billing_days)`, is the only way to delete from it, and it enforces the minimums itself.

### 7. Database roles (G-37)
- **The owner** (`POSTGRES_USER`) is the migrator. The `migrate` one-shot service runs with `DB_ROLE=owner`, after `db-roles`.
- **`db-roles`** is a one-shot over PostgreSQL's local socket, with no network and no owner password. It creates or updates:
  - `iptv_app`: the app services, `DB_ROLE=app` in `docker/app.env`;
  - `iptv_reporting`: read-only, without the credential tables.
- **Grants** are reapplied after every migration (`post_migrate` in `apps/ops`). `ALTER DEFAULT PRIVILEGES` covers new tables, and `pre_migrate` refuses to migrate as the app role.
- **What `iptv_app` can't do:** DDL, `TRUNCATE`, or rewriting and deleting audit rows. Partitions are created and dropped through `iptv_partition_create` and `iptv_partition_drop` (`SECURITY DEFINER`, limited to the partitioned tables).
- **Development** uses the same roles; tests run as the owner, and `test_privileges` checks the denials explicitly (SQLSTATE 42501).

### 8. Valkey ACL users (G-38, G-35)
- **Each Valkey's ACL file** is rendered at start (`docker/valkey/entrypoint.sh`, SHA-256 hashes, in tmpfs) with three users:
  - `default`: the operator, healthchecks and tests;
  - `app`: every command except `FLUSHALL`, `FLUSHDB`, `CONFIG`, `DEBUG`, `MODULE`, `KEYS`, `SHUTDOWN`, `ACL`, `MONITOR`, saving, replication and cluster administration;
  - `exporter`: the read commands redis_exporter needs.
  
  App services use `VALKEY_USER=app`.
- **Startup:** the entrypoint gives `/data` to the valkey user, because earlier files were root-owned, then drops privileges.
- **Memory:** redis-state gets `--maxmemory ${REDIS_STATE_MAXMEMORY:-1gb}` with `noeviction`, and the RedisStateMemoryHigh alert fires at 80%.

### 9. No Docker socket in application containers (G-36)
- **`docker-proxy`** (wollomatic/socket-proxy) serves Traefik: `GET` on `/version`, `/_ping`, `/containers/json`, `/containers/*/json` and `/events`, from Traefik only, on the internal `docker-api` network.
- **`docker-logs-proxy`** serves Alloy and CrowdSec: the same plus `/info`, `/networks` and `/containers/*/logs`, on `docker-logs`, from those two hosts only.
- **The proxies themselves:** they run as `0:0` (the socket is root-owned), read-only, with all capabilities dropped.
- **The exceptions,** documented in the monitoring overlay:
  - cAdvisor mounts the host's `/var/run`, `/sys`, `/var/lib/docker` and `/` read-only. It needs containerd's socket to name containers, and a read-only mount doesn't restrict a socket's API.
  - node-exporter reads the host's `/proc` and `/sys`.

### 10. Container hardening (G-39)
- **Every service, all overlays included:**
  - `cap_drop: [ALL]`, adding back only what it needs (for example `NET_BIND_SERVICE` for Traefik; `CHOWN`, `SETUID`, `SETGID` and `DAC_READ_SEARCH` for PostgreSQL, the Valkeys and the backup service);
  - `no-new-privileges`;
  - a read-only root with `tmpfs` where needed;
  - an image pinned by digest, Dockerfile `FROM` lines included.
- **The transcoder** stays on the internal `backend` network only (it needs the broker), with no internet.
- **`scripts/check_hardening.py`** (`make hardening-test`, in `make ci`) renders the production configuration alone and with every overlay, and fails on any service that misses one of these, mounts the Docker socket outside the allowlist, runs privileged or uses the host network.
- **Development** keeps writable roots for the app services (bind-mounted code, autoreload); everything else is identical.

### 11. CrowdSec (opt-in, on by default in the installer)
- **The overlay** (`docker/compose.crowdsec.yml`) adds the CrowdSec engine (v1.8.1-slim). It reads Traefik's container logs through `docker-logs-proxy`, with the acquisition matching `^/?smart-iptv-traefik-[0-9]+$`.
- **Detection:**
  - the hub's `traefik-logs`, `http-logs` and whitelist parsers, and `crowdsecurity/http-bad-user-agent`;
  - two local scenarios: `smart-iptv/http-4xx-flood` (capacity 120, refilling 1 every 2 s) and `smart-iptv/http-ratelimited` (40 `429`s, refilling 1 every 10 s).
- **The community blocklist** (`CROWDSEC_ONLINE`) is off unless the operator opts in, because it shares the attacking addresses with CrowdSec.
- **The bouncer** is the maxlerebourg Traefik plugin 1.7.1, vendored into our Traefik image as a local plugin (sha256-pinned), so nothing is downloaded at start. It runs in stream mode, fails open, and answers 403.
- **Control from the admin:** **Settings → Security** (`security.crowdsec_enforce`, `security.crowdsec_allowlist`).
  - The worker renders `crowdsec.yml` into a shared volume; Traefik's entrypoint copies it into the watched dynamic directory within 2 s.
  - The middleware is defined in both states (`enabled: false` when off), so routers never reference a missing middleware.
  - It renders on every `Setting` change of those keys (after the settings cache bump) and every minute.
- **Tested:** `make crowdsec-test` bans a test address, sees 403, switches enforcement off and on from the setting, unbans, and sees 200.
- **Unbanning:** `cscli decisions delete --ip`, documented in the installer's summary and the security runbook.

### 12. TLS and the host (G-43, G-42)
- **TLS:** `docker/traefik/prod/dynamic/tls.yml` sets TLS 1.2 minimum, ECDHE with AES-GCM or ChaCha20 only, and the X25519, P-256 and P-384 curves. With the existing one-year HSTS, that grades A+.
- **HSTS preload:** an explicit operator choice (`DJANGO_HSTS_PRELOAD=1` turns it on in both Django and Traefik).
- **ufw (the installer):** `default deny incoming`; SSH on each port sshd listens on, rate-limited or only from `--ssh-from` networks; 80 and 443.
- **SSH and disk encryption:** SSH settings are documented, not applied, so the installer can't lock the operator out. Host disk encryption is the operator's, on the security checklist.

### 13. Key rotation
`scripts/rotate-keys.sh <kind>` generates new values on the host, writes `.env` (mode 600) or `secrets/` without printing them, restarts what reads them, and records each step as `keys.rotate`, with the target being the kind (shown on Settings → System).

| Kind | Method |
|---|---|
| Media token | Stage a new `kid` that the edge accepts, promote it to signing 5 s later, and retire the old key only after the longest token lifetime plus 30 s (`--finish` refuses earlier). The key file is rewritten in place to keep its inode under Docker's secret bind mount |
| Django secret key | The old key goes to `SECRET_KEY_FALLBACKS`; `--finish` drops it |
| Field encryption | New key first, MultiFernet re-encryption of every encrypted model field and of the settings' secrets (`apps.core.services.reencrypt_secret_settings()`, CFG), a check that the new key alone decrypts everything, then the old key is removed |
| Database (app, reporting, monitor, owner) | Through `db-roles` or `ALTER ROLE` |
| Valkey (app, exporter, default) | `ACL SETUSER … >new` first, so both passwords work, then the consumers restart, then the Valkeys restart with only the new one |

Each kind was exercised on a throwaway compose project, with playback, sign-in, the stored secrets, migrations and backups checked afterwards. A script rather than an admin button: it edits files on the host and restarts containers, and Django has, deliberately, no Docker access.

## Alternatives considered
- **WAL-G** (Apache-2.0): a single binary, S3-first. Not chosen:
  - pgBackRest's `verify`, restore-to-name and time, count-based retention and repository encryption fit a drill-centred design better;
  - its local-repository mode is first-class;
  - one tool (restic) handles S3 for everything.
- **Barman** (GPL-3.0): only as a separate process, heavier, and it wants its own server.
- **Nightly `pg_dump` only:** no point-in-time recovery, and a day of data at risk. We keep a nightly dump inside restic as a second, portable copy.
- **Borg** (BSD): no native S3. **Kopia** (Apache-2.0): comparable to restic, but restic's `copy` between repositories and its maturity won.
- **An agent with its own cron:** two places to configure, and no admin visibility. Django scheduling keeps everything in the settings and the audit log.
- **Traefik's file provider instead of the Docker provider:** removes the socket entirely, but the dev stack and every overlay route by labels; a second routing source would drift.
- **tecnativa/docker-socket-proxy:** allows by API section (`CONTAINERS=1` opens far more than listing).
- **linuxserver/socket-proxy:** GPL-3.0.
- **fail2ban** (GPL-2.0): host-level, blind to container logs without extra plumbing, and no Traefik integration.
- **The CrowdSec forwardAuth bouncer container:** an extra hop per request.
- **Traefik's HTTP provider for the CrowdSec toggle:** Traefik would poll Django; a file in a shared volume keeps Traefik independent of web.
- **A separate migrator role distinct from the owner:** more roles for no gain on a single host; the owner already exists and only `migrate` and `db-roles` use it.
- **Per-service Valkey users:** web, worker and the relay need the same commands; one `app` user with a deny list is simpler to rotate.

## Consequences
- **The first update** on production builds three images (a few minutes; pgBackRest compiles from source) and recreates the stack once. PostgreSQL restarts with archiving, the Valkeys with ACLs, and the app services reconnect as `iptv_app` and `app`. The first full backup starts within a minute of the backup service's first poll. On the dev cluster (53 MB on disk, 5.7 MB stored) it took 3 s; it grows roughly linearly with database size. The first drill follows.
- **Disk:** the repository holds two weeks of fulls, differentials and WAL; at today's size that's tens of megabytes. Media backups (opt-in) are as large as the libraries.
- **Read-only roots:** anything a service writes must go to a volume or `tmpfs`, which new services must follow; `make hardening-test` catches regressions.
- **CrowdSec's limits:** Traefik's access log has no paths (they carry credentials and tokens), so path-based scenarios can't fire, and failed Xtream sign-ins return HTTP 200 by contract. What CrowdSec adds is bad user agents, 4xx floods, rate-limit abusers and, optionally, the community list; Xtream guessing remains Django's per-user and per-address limits.
- **The backup passphrase** can't be rotated in place; rotation means new repositories (runbook).
- **Tests run as the owner and Valkey `default`:** privilege checks are explicit tests, not a side effect of the test user.
- **Revisit:**
  - pgBackRest's own S3 repository when backups outgrow a local disk (M15's S3 origin);
  - per-service database roles if services split across hosts;
  - the cAdvisor exception if a socket-free container-metrics source appears.
